0) Decision and naming standard
Tenant-facing term (UI copy)

EN: Operating Model

ES: Modelo Operativo

PT: Modelo Operacional

Internal technical naming (choose one)

You have two paths:

Path A (recommended now): “Alias, don’t rename yet”
Keep DB tables as flightpath_* for now, but expose them in API/UI as “Operating Model”. Zero-risk migration.

Path B (later): Full refactor rename
Rename DB tables + code identifiers to governance_* / operating_model_*. Higher effort, more risk.

Do Path A now and schedule Path B after you stabilize integrations.

2) Add tenant setting for “governance model name” (optional but powerful)

Even if you standardize on Operating Model, letting tenants rename it (e.g., “Delivery Framework”) is a killer customization.

DB (tenant-scoped settings)

Add to your tenant settings table (whatever you now use, likely app_settings with tenantId):

governanceModelLabel (text, nullable)

Default value resolved as:

If tenant set label → use it

Else use locale default (“Operating Model” / “Modelo Operativo” / “Modelo Operacional”)

This is a small change with big perceived customization.

8) AI prompts: remove FlightPath branding in tenant-facing responses

Even if your internal system prompt calls it FlightPath, the AI output should align with tenant terminology.

Add to every AI call:

“In user-facing responses, refer to the governance lifecycle as: {Operating Model label}. Do not use the term FlightPath.”

This is critical—AI will leak the trademark otherwise.
